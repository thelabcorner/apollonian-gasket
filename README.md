## What this is

An Apollonian gasket is a fractal circle packing generated by repeatedly filling curvilinear gaps with circles tangent to three existing circles. This project turns that geometry into a responsive, explorable visualization designed to remain usable as recursion depth and visible circle count increase.

The deployed explorer has no framework, no runtime package graph, and no build step. Modern browsers use a WebGL2 renderer. If WebGL2 is unavailable, the same geometry automatically falls back to Canvas 2D.

## Highlights

- **WebGL2 GPU renderer** using instanced analytic circle rasterization
- **One instanced draw submission** for the visible gasket instead of thousands of Canvas arcs
- **Shader-based antialiasing** with no circle tessellation
- **GPU outline rendering** with exact per-circle screen-space widths
- **Geometry cache** that lets short pans and zoom bursts reuse existing circles
- **Render-only state changes** for palette, fill, and bounds controls
- **Relative-origin Float32 GPU coordinates** while preserving Float64 CPU geometry
- **Typed-array geometry buffers** instead of per-circle object allocation
- **Progressive interaction LOD** with full-detail refinement after input settles
- **Event-driven rendering** with no permanent idle animation loop
- **Automatic Canvas 2D fallback** when WebGL2 is unavailable
- **Eight color palettes**, keyboard controls, touch support, and extreme zoom
- **Zero runtime dependencies**

## GPU rendering architecture

The CPU remains responsible for the recursive Descartes geometry. The GPU is responsible for transforming and rasterizing every visible circle.

Each circle is uploaded as one compact instance:

```text
[x, y, radius, depth]
```

A four-vertex quad is instanced once per circle. The vertex shader expands each quad to the circle's screen-space bounds. The fragment shader then evaluates the exact radial distance and produces the circle analytically.

```text
input event
    |
    v
coalesced requestAnimationFrame
    |
    +--> camera state
    |
    +--> geometry cache hit? -----------------------+
    |          |                                    |
    |          no                                   | yes
    |          v                                    |
    |     Float64 Descartes generator               |
    |          |                                    |
    |          +--> screen-space pruning            |
    |          +--> fixed circle budget             |
    |          +--> typed arrays                    |
    |          |                                    |
    |          v                                    |
    |     relative Float32 instance upload          |
    |                                               |
    +-----------------------------------------------+
    |
    v
WebGL2 renderer
    |
    +--> instanced quad transform
    +--> analytic fragment-shader circle
    +--> shader antialiasing
    +--> palette lookup by recursion depth
    +--> optional analytic outline / bounds
```

### Why instanced quads instead of WebGL points?

`gl.POINTS` would be simpler, but maximum point size is hardware dependent and can be too small for the large circles visible near the root of the gasket. Instanced quads have no equivalent practical size limit and still keep geometry tiny.

### Why not tessellated circle meshes?

A tessellated circle wastes vertex bandwidth and either looks polygonal at high zoom or requires many segments. The current renderer sends four vertices per circle and evaluates the curved edge in the fragment shader.

### Why not WebGPU yet?

The workload is graphics-heavy but computationally simple. WebGL2 already provides instancing, shaders, robust browser support, and direct GPU rasterization. WebGPU would add asynchronous device initialization and a larger compatibility surface without removing the CPU-side recursive branching bottleneck. It remains a useful future path if gasket generation itself moves to GPU compute.

## Geometry reuse

GPU rasterization removes most drawing overhead, but repeatedly regenerating identical or nearly identical geometry can still waste CPU time during interaction.

The explorer therefore generates an overscanned region around the current viewport. Short pans and moderate zoom changes can reuse that cached geometry. In those frames, interaction becomes primarily:

```text
camera update -> uniform update -> GPU draw
```

Palette changes, fill toggles, and bounds toggles do not regenerate the gasket at all.

## Performance

The optimized CPU geometry generator was previously benchmarked against the original implementation at a 1920 × 1080 viewport. Geometry parity was preserved while reducing generator time by roughly **2.25× to 2.63×** across representative populated views.

| Zoom | Visible circles | Original | Optimized generator | Speedup |
| ---: | ---: | ---: | ---: | ---: |
| 0.9× | 2,599 | 1.668 ms | 0.652 ms | **2.56×** |
| 2× | 3,076 | 1.600 ms | 0.709 ms | **2.26×** |
| 5× | 3,056 | 1.702 ms | 0.690 ms | **2.47×** |
| 10× | 3,708 | 2.123 ms | 0.807 ms | **2.63×** |

Those figures isolate CPU geometry generation. The new WebGL2 renderer is an architectural rendering improvement rather than a claimed synthetic benchmark result. It replaces depth-by-depth Canvas arc construction with GPU instancing and analytic shader rasterization.

See [`PERFORMANCE.md`](./PERFORMANCE.md) for the full optimization breakdown.

## Precision strategy

Deep zoom creates a precision problem if large world coordinates are converted directly to Float32 GPU attributes. The renderer avoids that by keeping canonical centers and radii in Float64 on the CPU, then subtracting the geometry cache origin before converting positions to Float32.

```text
GPU position = Float32(circle center - geometry origin)
```

The camera is sent to the shader as a relative delta from the same origin. This keeps GPU values close to zero and preserves substantially more useful precision at deep zoom.

## Graceful fallback

WebGL2 initialization is attempted first with a high-performance GPU preference. If context creation or shader compilation fails, the renderer replaces the canvas and initializes the existing optimized Canvas 2D backend instead.

The UI exposes the active backend in the runtime statistics panel:

```text
Renderer  GPU
```

or

```text
Renderer  2D
```

## Descartes' Circle Theorem

For four mutually tangent circles with signed curvatures `k1`, `k2`, `k3`, and `k4`:

```text
(k1 + k2 + k3 + k4)^2 = 2(k1^2 + k2^2 + k3^2 + k4^2)
```

Given three tangent circles, the theorem yields the curvature of the alternate tangent circle. The explorer recursively applies that relationship, computes circle centers in the complex plane, rejects irrelevant geometry, and writes accepted circles into fixed typed-array buffers.

## Run it

No install is required.

```bash
git clone https://github.com/thelabcorner/apollonian-gasket.git
cd apollonian-gasket
```

Open `index.html` directly, or use any static HTTP server.

```bash
python -m http.server 8080
```

Then visit `http://localhost:8080`.

## Design goals

1. **Interaction latency** over framework convenience
2. **GPU rasterization** over CPU path construction
3. **Predictable frame cost** over unbounded visual work
4. **Mathematical parity** over unnecessary approximation
5. **Progressive detail** over freezing the UI to render everything immediately
6. **Graceful degradation** over requiring a specific graphics stack
7. **Small deployment surface** over a large frontend dependency graph
